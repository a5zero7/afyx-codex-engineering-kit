# Workflow: Discovery → Requirements → Design

Use for product discovery, a new feature, cross-team scope, system specification, or architecture decision. Skip irrelevant steps for smaller requests.

1. **Frame the outcome.** Confirm actor, problem, outcome, current evidence, constraints, and success criteria. Classify unverified statements as assumptions.
2. **Map requirements.** Identify roles and AS-IS/TO-BE processes, exceptional paths, business rules, privacy/security needs, and acceptance criteria. Resolve material contradictions with the requester or a documented assumption.
3. **Design appropriate level.** Choose a small viable set of options, compare tradeoffs, data and integration flow, permission boundaries, reliability, UX states, and measurable NFRs. Avoid gratuitous redesign.
4. **Decide and sequence.** Record choice, alternatives, scope/non-scope, dependencies, migration/rollout and reversibility. Define test and evidence required for acceptance.
5. **Deliver.** Provide decision-ready design proportionate to complexity, not an invented sign-off. For implementation handoff, include explicit acceptance criteria and unresolved questions.

Primary domains frequently include PM, BA, System Analyst, Architecture, UX, SME; select only those relevant to the work.
